# Database and security audit

Audit date: 2026-11-03. This began as a static review; a follow-up live check applied migration `202611030004_account_profiles_and_auth_audit.sql` to the configured Supabase project and verified its migration record, profile trigger, audit-table RLS, and authenticated RPC grant. This does not constitute a full production security review or end-to-end test with multiple accounts.

## Persistence and schema map

The app is hybrid when configured: browser `localStorage` is always used for its current store, Supabase Auth persists its own session, and authenticated rows are loaded from and upserted to PostgreSQL. Without both public environment values, the app is local-only.

The migration defines:

- `profiles` owned by `auth.users.id`.
- `learning_topics` with `user_id`, unique name per user.
- `study_sessions` with `user_id`, optional `topic_id`, denormalized topic/subject text, time/duration, difficulty, problem counts, reflection, and calculation version.
- `planned_sessions` and `weekly_reviews`, each user-owned.
- `xp_transactions`, readable by the owning authenticated user only; browser writes revoked.
- `audit_logs`, owner-readable and owner-insertable, with update/delete revoked from anon/authenticated.
- `auth_access_audit`, owner-readable and append-only to browser clients; signup records are written by the Auth user trigger, and authenticated account events are recorded through a server-side RPC. It stores no passwords or IP addresses.

All defined user tables enable RLS, and policies constrain the `user_id`/profile ID to `auth.uid()`. The new Auth trigger creates missing profiles and a signup audit row. This is a positive design signal. The frontend does not use an XP transaction ledger, does not set `topic_id`, and does not implement account deletion. There are no group membership/share tables, subject/module tables, storage buckets, or scoring RPCs.

## Findings

1. **High — synchronization can lose edits or resurrect deleted data.** Remote and local records are merged with local values winning for matching IDs. The upsert effect then writes that merged snapshot back to the server. There is no revision, conflict decision, outbox, or tombstone model. Local deletions are sent as best-effort direct deletes; failures can be swallowed and later uploads can restore data.
2. **Medium — topic foreign key does not prove tenant ownership.** `study_sessions.topic_id` references a topic UUID but has no composite owner constraint. The current UI omits `topic_id`, so it does not trigger the issue; a direct authenticated API client could associate their session with a known foreign topic UUID. Add a tenant-safe relationship before using that field.
3. **Medium — audit log authenticity is limited.** Owners can insert arbitrary self-owned audit records. RLS protects other users and prevents edits after insertion, but does not prove a logged before/after snapshot was generated by a trusted correction function.
4. **Medium — scoring settings are client-controlled and recalculated locally.** `xp_transactions` is protected from browser writes, but progression shown by the app is not a server-authoritative reward ledger. Do not use browser-derived XP as a paid, competitive, or tamper-resistant entitlement.
5. **Low — schema and defaults had one invalid fallback.** The `study_sessions.difficulty` SQL default was `Moderate` while its constraint allowed only `Easy`, `Medium`, `Hard`. The base migration and a new forward migration now set the fallback to `Medium`.

## Authentication and privacy boundaries

The app supports Supabase email/password registration, login, logout, password recovery, and session restoration when configured. Learning pages require an authenticated Supabase session; an existing signed-in account can still use its local cache offline. The account activity panel reads only the user's own audit rows. Sign-in, sign-out, password recovery, and password change entries are requested by the authenticated client, so those event types are useful account history but are not tamper-proof forensic logs. Signup rows are generated by a database trigger. Account deletion and profile-image workflow are not implemented.

The browser is configured only with the URL and public anon key. No service-role key was found. React escapes interpolated text by default, and no raw HTML rendering was found. Upload handling is not implemented. JSON export exports the current browser store and should not be described as a verified server-side account export.

## Required live verification

Before production: test two-user isolation for select/insert/update/delete; test topic cross-tenant association; configure and verify Auth SMTP and redirect/email settings; confirm backup/restore and account deletion; then add trusted, idempotent XP correction and audit RPCs. A live test using owned sign-in accounts was not performed here.
